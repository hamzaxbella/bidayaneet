# Nominal journey delivered for the hackathon

The implementation follows the supplied Processus_nominal_BidayaNeet document: identification, program entry, activation, orientation, accompaniment, actual activity entry and stabilization. Field mediators use the standalone React Native app; the web console reviews and manages synchronized dossiers. New youth registration remains absent from the web console.

The database change is additive: journey_events stores dated, actor-attributed observations without replacing young_people, offers or existing follow-ups. Existing demonstration records are not automatically assigned completed milestones. Each new observation has a durable UUID. Repeating the same request is idempotent; conflicting reuse is rejected. Partner accounts receive no journey observations, youth accounts can read only their own, and only an assigned mediator or administrator can record them.

Program entry records explanation of the program, the young person's commitment, an observation date and notes. Activation records confirmed activity participation, observed abilities, the clarified project and chosen pathway. Activity suggestions consider location, mobility, remaining capacity and the intended purpose; they require human discussion and do not certify attendance. Recommendations incorporate the observed abilities and project; a validated dossier, onboarding and activation are required before a new referral.

An accepted referral does not automatically record an activity start. The mediator separately records the actual start date, receiving organization, activity description, evidence and an agreed future verification date. The server derives the pathway type from the accepted opportunity. It schedules one follow-up at that date. Stabilization checks document continued or interrupted activity. A check before the agreed date remains a progress observation; continued activity at or after it confirms maintenance. A subsequent interruption changes the current displayed result and retains the earlier observations. The source document specifies no universal duration; the date is therefore explicitly chosen for each case.

Reports count documented activation, actual activity entry and confirmed maintenance. Attendance counts or generic legacy follow-up outcomes alone no longer mark these milestones complete. CSV exports include journey status and milestone dates. Evidence is declared by the accompaniers; it is not externally certified or an institutional integration.

The first onboarding, activation and insertion observations are immutable in this MVP. Further stabilization checks can be appended. Correction/reorientation workflows for these initial observations remain a future extension; avoid entering uncertain facts as final observations. Native stage writes require connectivity; new diagnosis collection and cached reads retain the existing offline behavior. Local SQLite encryption remains outside this change.

Verification covers the mobile API lifecycle, date ordering, evidence requirements, acceptance prerequisites, stable-ID retries, privacy and foreign dossier denial. Browser tests cover the complete dated workflow and a control before the maintenance deadline. Historical test observations are explicitly fictional and kept in an isolated database. No real sustained insertion is claimed by these tests. Physical Android installation, airplane-mode restart and final synchronization still require device validation.
